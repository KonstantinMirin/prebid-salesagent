Adversarial review: “Where the generator loses the schema, and where to stop it”

Review of docs/audits/sdk-codegen-design.html at 610219f44 (branch docs/sdk-codegen-design), read in full before any measurement. Every measurement below was taken in a fresh clone of adcontextprotocol/adcp-client-python at 0c7e8b86d (9.0.0b2, bundle schemas/cache/3.2, 1,625 schema files), at a sibling directory sa-sdk-review-clone, in an isolated virtualenv (pydantic 2.13.5, jsonschema 4.26.0, CPython 3.12.9), 2026-10-10.
EXECUTION means I ran it in that tree and the output is quoted. READING means I read source, issue text or git history and did not run it. Nothing below is inferred from the design document's own figures.

Summary

The design’s diagnosis is right and better-grounded than most of what it reviews: #1409 and #1414 are one defect, #1362 was the sibling, #1359 is an aggregate. The recommendation is where it fails. Option A does not make the defect unconstructible; it makes the next unseen shape detectable while re-admitting the twelve present ones by permission, and I measured that even the detection does not work: an existing predicate in the conformance suite classifies the entire #1414 divergence class as already-declared, so adding the field-removal mutations the design asks for leaves the suite green. It is green today, over 41,667 documents, with the defect live.

Three of the four objections the design raises against Option B are refuted by code already shipped in the repository. src/adcp/types/versioned.py contains a @model_validator(mode="after") that serializes the model and runs the bundled jsonschema validator over the result, rendering the jsonschema error as a pydantic field error. That is Option B, in production, inside adcp.types. And the decision the design treats as prohibiting it — #1102, as written up in docs/validation-contract.md by the repository owner — contains a paragraph asking for exactly this on exactly this class of semantics.

1. Verdicts on the five questions

Q1. Does the recommended fix make the defect unconstructible, or only detected?

ONLY DETECTED — and the detection is measurably inert

Option A has three parts, and they are three different kinds of thing:

PartKindGrade
Widen _root_required_groups to per-arm not.required exclusions and sibling consts A better projection Not structural. Projection is the defect's mechanism. A wider projection has a different boundary, not no boundary.
Generation fails on an arm condition the extractor cannot express A refusal Structural for shapes not in the residue. This is the one part that makes something impossible.
Shrink-only residue set naming schema + pointer + keyword A ledger A ledger. It is the mechanism by which the twelve present defects stay present, with a name.

The residue is not the pattern the design claims it is. The design calls it “exactly the manifest pattern the repo already runs for fix effects.” It is not the same kind of artifact. tests/conformance/_schema_parity.py’s DECLARED holds 8 predicates over causes — EXECUTION 8 entries, each a Callable[[Divergence], bool]. The post-generation effect manifest records measured effects of passes. A residue naming create-media-buy-request.json + /anyOf/0/properties/packages/items/allOf/0 + required is an instance ledger, and the repository already has one of those and it already failed:

EXECUTION Three entries, all one tool. docs/validation-contract.md § “Maintaining the boundary” says: “Any payload accepted by Pydantic but rejected by the canonical schema must be listed in the narrow checked-in divergence allowlist with its lost JSON Schema keyword.” #1414 is such a payload. It is not listed. The repository has been in violation of its own written contract since #1368 merged on 2026-10-04, and the ledger did not notice, because a hand-written ledger has no way to notice. Adding a fourth such ledger is adding a copy of the instrument that missed it.

The measured break: the behavioral grader is already blind to this class

Option A’s step 3 is what the design says keeps the residue honest: add field-removal mutations to the parity corpus, “so a divergence with no entry fails the suite.” It would have an entry. EXECUTION:

DECLARED["union_arm_absorbs_a_type_error"] is lambda d: d.direction == MODEL_ACCEPTS and d.keyword in ("oneOf", "anyOf"). The jsonschema keyword that refuses a branch-membership failure is anyOf, so this predicate covers every root-composition divergence regardless of cause. Three consequences:

  • Closing the corpus hole does not surface #1414. The suite stays green.
  • The residue set is never graded behaviorally, under Option A or any other option, while that predicate stands.
  • The stale-entry test will not ask for the predicate's deletion, because it keeps matching the real type-absorption divergences it was written for. It is a correct entry that is also too coarse.

Option A therefore needs a fourth change the design does not list, and that change is itself a hand-written discrimination in the same family: teach the predicate to tell “the mutated leaf's type broke every arm” from “the document's field set satisfies no arm.”

The suite's present state makes the point without argument. EXECUTION, driving its own grading machinery over every graded tool on 0c7e8b86d: 41,667 documents compared, 1,744 divergences, zero of them undeclared — the suite is green — while CreateMediaBuyRequest accepts a document its own bundled schema refuses. union_arm_absorbs_a_type_error accounted for 73 of those 1,744, so it is a live entry no stale-entry test will ever retire. Full figures in §2.

What the defect actually is, structurally

The pipeline does this, in this order:

  1. scripts/generate_types.py holds _ROOT_OBJECT_VALIDATION_UNIONS, a hand-listed set of 8 schema paths (EXECUTION 8 entries, including media-buy/create-media-buy-request.json).
  2. flatten_root_object_validation_union deletes the root composition from each, because codegen 0.63+ renders it as a RootModel union and that breaks the subclassability contract.
  3. scripts/post_generate_fixes.py re-reads the original schema and reconstructs a projection of what step 2 deleted.

Information is destroyed on purpose and then partially rebuilt. No improvement to the reconstruction makes “reconstruction weaker than the original” unconstructible, because reconstruction is the mechanism. The only shapes of fix that remove the class are: stop destroying it, or evaluate the undestroyed original. Option A is neither. Its generation-time refusal is a genuine structural gain over today — a new unexpressible shape goes red — and that gain is real and worth having; it is just not the same thing as the defect becoming unconstructible.

Q3. Is the #1102 boundary binding against the permanent alternative?

No. The decision is real, maintainer-authored and documented — and its own text asks for construction-time validation on this class of semantics.

READING #1102 was closed COMPLETED on 2026-09-03 by 0e003a5f5 fix(validation): enforce canonical schema boundaries (#1117), authored by Brian O'Kelley, which wrote docs/validation-contract.md. So this is a real decision by the repository owner, not a convention. The design is right about that, and right that it chose option 2: canonical schemas define wire validity; generated models are structural application types.

Four paragraphs later, the same document says:

“For irreversible commitments, authorization, signing, and billing semantics, prefer an additional targeted runtime validator so invalid state fails during ordinary model construction as well as at the wire boundary. These targeted checks supplement canonical validation; they do not change which artifact is the protocol source of truth.”

create_media_buy is an irreversible commitment with billing semantics; #1414's own downstream symptom is a budget-floor error code answered for a request that carried no budget. The design's objection (1) — that Option B “makes the model a second wire boundary” and re-litigates #1102 — is answered in advance by the sentence that follows the decision it cites. Construction-time validation is pre-authorized for this category, and the document pre-empts the source-of-truth worry explicitly.

Two of the design's three remaining objections are also already answered, by shipped code.

READING src/adcp/types/versioned.py:353, _VersionedExtensionModel._validate_schema_document — a real field-based pydantic model built by create_model:

  • Objection (3), jsonschema pointers split the error vocabulary: this code converts the jsonschema error to path: message and raises ValueError, which pydantic wraps as an ordinary field-level ValidationError. The precedent for the error shape exists too.
  • Objection (4), keyword construction has no document to grade: _protocol_payload() builds one from the constructed model, with exclude_unset=True, which preserves exactly the field-presence information a root required/not condition reads. The design's narrower worry — that a round-trip can mask an author error the serializer erases — is true in general and does not apply to root composition, which is a question about which fields are set.

The design also understates its own measurement. It says layering “does not forbid” Option B because adcp.types imports adcp.validation in four modules. EXECUTION confirms four, and three of them import adcp.validation.schema_loader — the compiled-validator machinery Option B needs:

The honest limit on the precedent: VersionedSchemaModel's docstring scopes it — “intended for boundary validation and schema generation, not as a base class for adopter-defined models” — and these are the negotiated non-pinned-version models, not the pinned generated tree. So the precedent does not authorize Option B by itself. It does remove the layering objection, the error-vocabulary objection and the cost-is-unprecedented objection, which is three of the four reasons the design gave for ruling it out.

Measured. Small in absolute terms, large as a ratio on small documents, and 12% of a cost most adopters already pay per call.

Reading those four ways, because they lead to different conclusions:

  • Against Option B: on a small document pydantic validates in 9µs, a 64–69µs root check is a 7.6× slowdown. The design's “construction cost on every instantiation” is a real floor, not an adjective, and it does not shrink with the document. A server constructing many small models internally pays it every time.
  • For Option B: 64µs is 12% of the 548µs full-schema validation that docs/validation-contract.md says serve(), create_mcp_server() and create_a2a_server() all run by default on both sides. For any adopter on those paths the marginal cost is noise against a cost already accepted.
  • The expensive half is the dump, not the check: keyword construction costs 168 + 64 = 232µs. If Option B is scoped the way the design's own fallback scopes it — model_validate-from-document only — the dump never happens and the cost is 64µs.
  • Correctness is unaffected by scope: EXECUTION the anyOf-only subschema accepts the valid synthesized payload and refuses #1414's document. 3 arms, 3 root allOf items.

Net: the cost objection survives as a reason to scope Option B, not as a reason to reject it. It is also the one objection the design raised that I could not refute from the repository.

3. Recommendation

Delete the projection rather than widen it. Carry the root composition to the model and evaluate it, scoped to the root subschema, with one validator in src/adcp/types/base.py. That is the design's Option B, narrowed to the scope its own fallback names, and promoted from fallback to the fix. Option D for #1409 stands as written, with the count corrected to 39 and composed with the existing GeoPostalArea shim.

Concretely, and in landing order:

  1. Narrow DECLARED["union_arm_absorbs_a_type_error"] first, and watch it go red. This is the measurement instrument, and it is currently returning the wrong answer for the defect under discussion. Until it discriminates branch-membership failure from type absorption, neither Option A nor Option B can be graded. Do this before anything else, and confirm it goes red on the #1414 document — the probe above is five lines.
  2. Add the field-removal mutations to MUTATIONS' sweep (delete one optional leaf at a time). With step 1 done, this is what makes the whole class visible; without step 1 it changes nothing.
  3. Replace enforce_root_required_groups' emitted tuple with the arm subschema itself. The post-generation pass stops deriving anything: it writes the root composition onto the class as data (a class-level reference identifying the schema and pointer), and one hand-written @model_validator(mode="after") in base.py evaluates it through adcp.validation.schema_loader against the document. Copying a JSON node cannot be lossy; the 7,522-line post-processor loses its reason to have an opinion about which keywords are expressible, and the review surface becomes one function instead of an extractor plus an emitter plus a residue.
  4. Scope it to the document path. Validate when model_validate has a document (64µs). For keyword construction, follow the existing precedent and build the document with _protocol_payload() (+168µs) — or, if that cost is refused, run the check on the document path only and say so in validation-contract.md. That is a maintainer's call on a measured number, which is the right shape for it to be.
  5. No residue set. There is nothing left to record: the condition is carried verbatim, so there is no remainder. The three entries already in validation-model-divergences.json become removable for the root-composition cause, and type-generation.md's refusal of a third hand-maintained allowlist stays intact.
  6. Then Option D, as the design sequences it.

Why this and not Option A: Option A's structural part (generation fails on an unexpressible shape) is the right instinct applied one level too late. If the keyword is carried rather than projected, there is no such thing as an unexpressible shape, so there is nothing to fail on and nothing to record. The measured facts that push me here rather than to the design's position are the three refuted objections — the mechanism is shipped, inside adcp.types, with the error shape already solved — plus validation-contract.md's own paragraph asking for it on commitment semantics, plus the finding that Option A's behavioral guarantee does not currently execute.

The strongest argument against my recommendation.

The 64–69µs is not amortizable and does not shrink with the document, so it is a 7.6× slowdown on the small-model construction a busy seller does most of. Pydantic validation of a 6-key request is 9µs today; it becomes 73µs. If a request handler constructs a few dozen small models, the schema delegation becomes the dominant cost of request parsing, and unlike the 548µs wire check it cannot be turned off with ValidationHookConfig because it lives inside the model. Option A costs microseconds — a tuple comparison over model_fields_set — and the maintainer who wrote defer_build=True into AdCPBaseModel specifically to keep model cost down ("with ~700 generated model modules, eager builds dominate import adcp memory") has demonstrated that this cost dimension is one they actively manage.

There is a second, sharper version of the objection: carrying the arm subschema verbatim means carrying its $ref graph, and the arms reference other schema files. So step 3 either ships a resolver with each class or reads the bundle at validation time — at which point it has become “evaluate the bundled schema,” and the claim that the post-processor “only copies a JSON node” is thinner than it sounds. I think the bundled-schema read is the right answer (schema_loader already caches resolved per-tool validators, which is where the 64µs steady state comes from), but it does mean the model's correctness now depends on the shipped bundle's file layout, which the projection did not.

If the maintainer takes the cost objection, Option A plus my step 1 and step 2 is a defensible second-best — strictly better than the design as written, because the design's behavioral guarantee does not execute without them.
