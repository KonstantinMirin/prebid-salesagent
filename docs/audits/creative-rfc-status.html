Creative RFC status in this seller, and whether the format_id / format_kind duality is fully supported

Read-mostly audit. Worktree sa-crfc, branch audit/creative-rfc, HEAD 390fa2519. Pin: AdCP spec 3.2.1 via adcp==9.0.0b1+prs1435.1415.1456 (pyproject.toml:10). No code was changed. No guard weakened, no allowlist grown, no xfail or skip added.

Evidence marking

Every claim below carries EXEC (I ran it in this worktree and the output is reproduced or summarized) or READ (I read the source or the schema). Code claims cite file:line; obligations cite the spec document and version.

Summary

Q1 — how much of the Creative RFC is complete. The legacy half is substantially complete and well factored: one canonicalization implementation, one identity type, one persistence mapping, and the comparison-heavy paths all route through them. The canonical half — which is what AdCP 3.2 actually asks a seller for — is a thin shell. Of the 24 obligations graded below: 4 implemented, 7 partial, 13 absent. Nine of the implemented-or-partial ones have no grading test of any kind. The 3.2 authoring direction is inverted relative to the spec: format_ids is this seller's authored catalog and format_options is an opaque pass-through document, where the spec requires canonical authored and legacy derived.

Q2 — is the duality fully supported? No. Both directions exist and the canonicalization helper is correct, but the canonical direction loses data at the persistence edge in a way that makes the round trip fail. Verified by execution: a creative synced with format_kind + format_option_ref cannot be read back — the stored document drops the scope discriminator the pinned schema requires in both arms, and reconstructing the listing response raises union_tag_not_found. Nothing in the tree grades it, because no BDD scenario sends a canonical creative at all.

One thing the duality gets right, stated positively because it was measured rather than assumed: the library's canonical boundary models silently delete format_id / format_ids / v1_format_ref from anything they serialize, including from a plain dict handed to them unvalidated — and this seller cannot reach that path. Zero canonical classes appear in the transitive closure of all 14 tool DTOs and return types (1093 models walked), every base is pinned to a Legacy* spelling on purpose, and format_ids demonstrably survives the real get_products wire. That immunity is unpinned by any guard, and the creative migration is the change that ends it — Q2.5 and gap 9.

Q2 — is the format_id ↔ format_kind duality fully supported?

No. Taking "fully" as the stated bar — both directions work and neither can be silently lost — the duality fails on the second clause in two distinct ways, one of which is a hard failure rather than a silent loss.

2.1 — Where does format_kind come from, and what happens when declared and derived disagree?

Both, and the design keeps them apart correctly. READ + EXEC

  • Declared by the buyer, read straight off the request DTO: src/core/schemas/_base.py:735 (declared_kind = creative.format_kind), carried through the sync gate unchanged at src/core/tools/creatives/_validation.py:81.
  • Derived from a format_id by canonical_kind_for (src/core/format_resolver.py:110-172), which runs only the two normative steps it can: step 1, the agent's own canonical.kind on a fetched spec; step 3, the registry glob fnmatch(legacy_id, pattern.format_id_glob). Otherwise ValueError, caught at :189-200 and left as kind = None.
  • Read off the SDK only as the vocabulary: is_canonical_format_kind and CanonicalFormatKind (_base.py:47,91), passed as a parameter rather than used as an annotation — which is exactly what PR #1415 asks for.

They cannot disagree, by construction, and that is the right answer. This is the key difference from #2355. There, a declared brand_json_url was compared against a derived one using rstrip("/"), so the rule was simultaneously too lenient and too strict. Here the two values are never compared at all, because the two arms are mutually exclusive on the wire: a creative carries format_id or format_kind, never both (EXEC, verified both branches refuse — Q1 row M4), so a derived kind only ever exists alongside a format_id, and a declared kind only ever exists alone. CreativeFormatIdentity is one type with an assertion field marked compare=False (_base.py:577-581) rather than a two-arm union, "because the projection between the two identities runs one way only" (:540-544).

The exclusivity is then re-asserted exactly once on the way out, by wire_format_kind (_base.py:630-649): return None if self.assertion is not None else self.kind. EXEC — an identity holding both (kind='image', assertion display_300x250) emits wire_format_kind = None. So a legacy creative never emits a derived kind beside its retained assertion, which is what the response model's oneOf requires.

One residual asymmetry worth naming, not a defect: on the product side the two can disagree, because format_ids and format_options are independently authored (Q1 row F4). That is the state FORMAT_DECLARATION_DIVERGENT exists for, and we neither detect nor report it (row E1). The declared-vs-derived hazard therefore does exist in this subsystem — on products, not on creatives.

2.2 — Does format_kind survive the wire in both directions?

format_kind: yes. format_option_ref: no — and the failure is loud, not silent.

No exclude=True hides it

EXEC + READ — git grep "exclude=True" src/core/schemas/ returns 20 field-level exclusions and not one is on format_kind, kind, format_option_ref, format_option_id or format_options. Executed probe:

CreativeAssetRequest wire keys: ['assets','creative_id','format_kind','format_option_ref','name']
  format_kind: image | format_option_ref: {'scope': 'product', 'format_option_id': 'opt1'}

Inbound and outbound on the request model are clean. The only suppression is the deliberate oneOf one in wire_format_kind.

The persistence edge drops the scope discriminator

EXEC — the full round trip, run in this worktree:

c = CreativeAssetRequest.model_validate({... "format_kind":"image",
      "format_option_ref":{"scope":"product","format_option_id":"opt1"}})
ident = creative_format_identity(c)
  -> CreativeFormatIdentity(kind='image',
       option=FormatOptionIdentity(publisher_domain=None, format_option_id='opt1'),
       legacy=None, legacy_parameters=(), assertion=None)

  -> {'format_kind': 'image',
      'format_option_ref': {'publisher_domain': None, 'format_option_id': 'opt1'},   # no 'scope'
      'legacy_format_id': None, 'legacy_format_key': None}
CreativeFormatIdentity.from_row(row)   # identical to ident -- the loss is invisible here
jsonschema validate(cols['format_option_ref'], core/format-option-ref.json)
  -> INVALID: is not valid under any of the given schemas

Two faults in one document, both from FormatOptionIdentity.document (src/core/schemas/_base.py:524-527), which emits only publisher_domain and format_option_id:

  1. scope is absent. The pinned core/format-option-ref.json is a discriminator: {propertyName: "scope"} union and scope is in required on both arms. A comment at _base.py:748-751 asserts the arms have "identical three-field sets, differing only in the scope discriminator" — true of the declared fields, but the discriminator is the one field that is not optional.
  2. publisher_domain: null is present on the product arm, which forbids it. The product-local arm carries "publisher_domain": false — a schema-level forbid, not an absence.

src/core/tools/creatives/listing.py:622 then emits that document raw onto the response (format_option_ref=db_creative.format_option_ref). EXEC — the response model refuses it:

Creative(format_option_ref={'publisher_domain': None, 'format_option_id': 'opt1'}, ...)
  -> ValidationError: format_option_ref
     Unable to extract tag using discriminator 'scope' [type=union_tag_not_found]

Creative(format_option_ref={'scope':'product','format_option_id':'opt1'}, ...)
  -> ACCEPTED, wire = {'scope': 'product', 'format_option_id': 'opt1'}
Creative(format_option_ref={'scope':'publisher','publisher_domain':'p.example','format_option_id':'opt1'}, ...)
  -> ACCEPTED, wire = {'scope': 'publisher', 'publisher_domain': 'p.example', 'format_option_id': 'opt1'}

So: a creative that syncs successfully with format_kind + format_option_ref cannot be listed. The path is reachable end to end and deliberately so — _validation.py:74-81 and :136-147 were written to accept the canonical arm, with the comment "Carrying only format_id made a canonical creative unrepresentable". A canonical creative without a format_option_ref lists fine, because the column is then NULL. The break is specific to the exact-routing case the spec calls for whenever a product has multiple same-kind options.

Nothing grades it. git grep format_kind tests/bdd/features/ returns 9 lines in 3 files and none sends a creative identified by format_kind: BR-UC-018-list-creatives.feature:749 names format_kind and format_option_ref only as members of a fields selector array, and the Then step's assertion list (tests/bdd/test_uc018_list_creatives.py:2271-2287) is 10 hardcoded fields that include neither; the <format_kind> column in local-uc006-dry-run-out-of-transaction-effects.feature takes the values generative/static and is not the AdCP enum (tests/bdd/steps/domain/uc006_sync_creatives.py:3435). The factories only ever derive the column from a legacy format_id (tests/factories/creative.py:61,147).

2.3 — Is a format reference ever compared by raw string equality?

Mostly no — the canonical path is genuinely single-sourced — with one live spec violation and two lower-severity ones.

The helper is correct and is the only builder of a key. EXEC:

https://creative.adcontextprotocol.org        -> 'https://creative.adcontextprotocol.org/\x1fdisplay_300x250'
https://creative.adcontextprotocol.org/       -> 'https://creative.adcontextprotocol.org/\x1fdisplay_300x250'
https://CREATIVE.adcontextprotocol.org        -> 'https://creative.adcontextprotocol.org/\x1fdisplay_300x250'

2.5 — Can a declaration lose its scope by passing through a position where the value is not the canonical model?

Not in this seller, and not by luck. The hazard is real in the library, our tree cannot reach it, and the reason it cannot is written down in the code. Two separate things have to be said, because they do not agree.

The upstream change, and what the False default actually gates

READ — commit 19e4b62ee8f52b90f3997a6132262e72f54d4302 on adcp-client-python PR #1447, "read the format-declaration scope defensively in the wrap serializer", in src/adcp/types/canonical_creative.py:

-   _format_scope=type(self).__adcp_format_declaration_scope__,
+   _format_scope=getattr(type(self), "__adcp_format_declaration_scope__", False),

Its reason: "A field annotated with a canonical model can hold a plain dict, and pydantic then hands that dict to the wrap serializer. Reading the class-level capability directly raised AttributeError on 'dict'; the class-name comparison it replaced was safe only by accident, since 'dict' != 'Format'." Its regression test reaches that state with Response.model_construct(affected_packages=[{"package_id": "pkg_1"}]) — model_construct, which skips validation. EXEC — the commit is the fourth-to-last on the branch and the head (dcec537cd) is after it, so the defensive read is in the PR head.

The defensive read is correct at a library boundary and should not be scored as a data-model smell. Pydantic tolerates a mismatched value during serialization with a UserWarning rather than raising, and model_construct is a public, documented pydantic API. A serializer that converts pydantic's warning into an AttributeError is escalating a tolerated state into a crash, which is a library defect independent of whether any caller should be in that state. EXEC — confirmed on our pin: a dict at a canonical position emits one UserWarning and dumps, and type({}).__name__ == "Format" is False, so the class-name comparison the ClassVar replaced was indeed silent rather than safe.

But the False default is output-inert, at our pin and at the PR head alike — so it cannot currently produce quietly-wrong output. This is the part worth stating precisely, because it bounds the concern rather than dismissing it. _format_scope is a seed threaded through strip_legacy_creative_identity and never consulted in a condition:

  • READ At our pin, .venv/.../adcp/types/canonical_creative.py: declared at :312, propagated at :330, :341, :350. The two decisions in that function read is_legacy_creative_identity_key(key) (a regex, :213: (^|_)(?:format_ids?|v1_format_ref)($|_)) and _is_format_scoped_agent_tuple(value, path=path) (:283, which takes path, not the seed). Neither reads _format_scope.
  • READ At the PR head dcec537cd, fetched and inspected: identical — declared at :358, propagated at :376, :387, :396, consulted nowhere.
  • EXEC Proof on our pin, same document both ways: strip_legacy_creative_identity(doc, _format_scope=True) == strip_legacy_creative_identity(doc, _format_scope=False) → True.

The ClassVar's two consequential readers are on the validation path, not the serialization path — PR head :571-573, allow_root_v1_ref=cls.__adcp_format_declaration_scope__ and format_scope=… feeding _legacy_creative_identity_path inside a @model_validator(mode="before"). That is what lets Format keep a root v1_format_ref where every other canonical model rejects it, and it reads cls, so a dict can never substitute for the class there. The other two serializer readers (:585, :594) are left undefended and correctly so: they are model_dump / model_dump_json instance methods, unreachable with a dict as self.

So the loss is real, and it runs through a different mechanism than the scope

EXEC — a dict at a canonical position on our pin:

class R(BaseModel): affected_packages: list[canonical_creative.Package] | None = None
R.model_construct(affected_packages=[{"package_id":"pkg_1",
                  "format_ids":[{"agent_url":"https://a.example","id":"x"}]}]).model_dump()
  -> {'affected_packages': [{'package_id': 'pkg_1'}]}      # format_ids DELETED
  -> warnings: ['UserWarning']

The format_ids key is gone. That deletion is is_legacy_creative_identity_key doing its job on an unvalidated dict, not the scope seed being misread — it happens identically whichever way the seed is set. The hazard is "the strip runs at all on a value that never went through validation", and the scope default is a latent second-order risk on top of it: if a future SDK version makes _format_scope consequential on the serialize path — the obvious candidate being to mirror allow_root_v1_ref so a Format keeps its root v1_format_ref on output — then the False default silently flips a declaration's output from "keeps v1_format_ref" to "strips it". The PR's test asserts only that the call does not raise; it asserts nothing about whether the output is right for a dict that genuinely carries a declaration. That prediction is recorded here so it can be checked against the next bump rather than rediscovered.

EXEC — adcp.types.ProductFormatDeclaration is adcp.types.canonical_creative.Format: a pure alias. One correction to Q1 row S1 that this probe produced: format_options is opaque at storage and at product_conversion.py:427, but it is not opaque at the model layer — the inherited annotation validates it into ProductFormatDeclaration1..16 and the wire output is that branch's dump, with the generated class's defaults filled in (the probe above shows canonical_formats_only, experimental, v1_translatable, synthesis_nondeterministic and a full slots array that the stored document did not contain).
