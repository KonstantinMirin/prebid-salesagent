One class per schema branch: request generation in the adcp SDK

Solution design · adcp-client-python at 9.0.0b2 · bundle schemas/cache/3.2 (1,509 non-bundled files) · measured in a fresh clone at 00720022b (branch fix/anyof-branch-conditions; upstream main 0c7e8b86d) · supersedes the constraint-compiler design (codegen-solution-design.html), whose census this reuses and re-derives. Terminology: a schema’s anyOf/oneOf members are called branches throughout.

The generator renders a response root’s branches as one class each and a union (CreateMediaBuyResponse = CreateMediaBuyResponse1 | 2 | 3), but flattens a request root into one class — CreateMediaBuyRequest: 31 fields, every branch-discriminating field optional — and then bolts on a validator that reads only each branch’s required key and discards the rest. The flattening is what creates the validator’s job. This design deletes the job: every flat-root combinator schema is emitted as one class per branch plus a union alias, so the branch content stops being a rule and becomes a type. Measured over the whole affected population: all 247 branch-level keyword occurrences dissolve into types; zero survive as runtime checks. What survives as checks is the root conjuncts beside the combinator (41 occurrences), and those keep the constraint compiler — shrunk to that jurisdiction, with the closure rule unchanged: compiled, classified by a named rule, or UnexpressibleKeywordError. No skip lane, no ledger.

The honest totals: 247 of 247 branch-level occurrences become types; 41 root-conjunct occurrences survive as compiled checks across 17 schemas; 24 root-conjunct occurrences dissolve (14 inheritance, 10 distributed presence logic). The branch-class design therefore does not delete the constraint compiler of the superseded design — it shrinks its jurisdiction from “everything, including the combinator” to “root conjuncts only,” and relocates its output onto the branch classes. The combinator content — where the chased defect lived, and where all five red parity cases sit — is types.

2.2 · The extra='allow' caveat, stated plainly

The generated models are extra='allow' (the schemas say additionalProperties: true; forward compatibility is the SDK’s deliberate choice, and this design does not change it). Under extra='allow', merely omitting a field from a branch class does not refuse a wire document that carries it — pydantic would file proposal_id under extras and accept. So the 19 absence occurrences (plus the 7 distributed outright bans) are enforced in two layers, and the claim for each layer is different:

  • At construction, absence is a type. The branch class does not declare the field; the pydantic mypy plugin and every IDE refuse the keyword argument. There is no spelling of CommittedProposalExecution(packages=…) that typechecks.
  • At wire validation, absence is one shared check. Each branch class carries a node-derived frozen set (_absent) and the base class carries one mode='before' hook, written once in src/adcp/types/base.py, that refuses a listed key present in the raw document — present with any value, explicit null included, which is exactly JSON Schema’s not:{required} semantics. This is a check wearing the census’s “absence” label, and the count above says so rather than hiding it: it is the one place the type system alone cannot carry the branch content, because the type system does not see raw documents. It is one primitive, not per-site logic, and the alternative — extra='forbid' on branch classes — would refuse spec-permitted unknown fields, a different behavior change this design does not smuggle in.

3 · Names: every branch, from its node — a folded-in prerequisite

The naming rule exists, designed and measured under #1409 (scripts/union_arm_names.py, branch claude/issue-1409-union-arm-naming; measured 557 root-level branches bundle-wide: 169 by title, 82 by discriminator const, 27 by required set, 278 creating no class, 1 refused). Two amendments, both forced by this design and both mechanical:

  1. Step zero inverts for flat-root combinator schemas. The rule’s step zero says a branch introducing no new property is a validation branch and must mint no class — correct when a flat root class exists for it to refine. Under this design the flat root class no longer exists: the branch is the request shape (the merged root properties plus the branch’s modifications), and the class names exactly what a buyer sends. On a flat-root combinator schema, every branch mints a class.
  2. One new rung, still node-derived. Naming rungs stay title → discriminator const → full sorted required set, each prefixed with the parent model name (the title rung too: response-branch titles already carry their stem — CreateMediaBuySuccess — but request-branch titles are prose, and a bare CommittedProposalExecution on the flat surface does not say what it is; parent + PascalCase(title) is as mechanical as parent + const). Rung 3b: a branch whose only content is a nested required overlay is named parent + property + its sorted nested required set. One branch in the population needs it.

4 · Discriminated union or plain union, per schema

Measured: a pydantic discriminated union needs one field required in every branch with a distinct const per branch. Three schemas of 43 have one:

SchemaTagValues
brand/verify-brand-claim-request.jsonclaim_typesubsidiary / parent / property / trademark
account/list-account-changes-response.jsonstatuscompleted / failed
media-buy/get-reporting-status-response.jsonstatuscompleted / failed

Those three get Annotated[Union[…], Field(discriminator='…')]: single-pass dispatch and a one-line no-match error naming the tag. create-media-buy is not one of them — branches 0 and 1 differ by a const nested inside an optional object (budget_allocation.mode), branch 2 by the presence of proposal_id; there is no shared top-level tag, and inventing one would invent a spec field. (A pydantic Discriminator with a callable could synthesize dispatch, but the callable’s logic is hand-authored semantics per schema — the thing this design exists to stop. Refused.)

Everything else is a plain union in left-to-right mode (union_mode='left_to_right'), not smart mode, for one reason: determinism of the returned class. The anyOf schemas of the at-least-one-of idiom (§6) have overlapping branches — a control_media_buy document carrying both paused and total_budget satisfies two branches — and smart mode’s match choice is a scoring heuristic. Left-to-right is the schema’s own order, stable under regeneration of the same bundle, and JSON Schema anyOf semantics exactly: accepted iff at least one branch accepts. For oneOf roots, exactly-one must also hold: every oneOf in the population is pairwise disjoint by construction (distinct required consts, or mutual absence sets — verified branch by branch in the census), so at-least-one equals exactly-one and the union is the full semantics. The emitter proves that disjointness from the Arm records when it renders a oneOf as a union; a oneOf it cannot prove disjoint refuses generation (UndisjointOneOfError(file, pointer) in the same family as UnexpressibleKeywordError) rather than shipping anyOf-weaker semantics. Zero refusals fire at the pin for this population. The 22 existing response-union modules keep their current contract (cross-branch exclusivity carried by wire validation) until they pass through the same emitter in the landing series.

4.1 · The no-match error: the consumer’s whole diagnostic

When no branch matches, pydantic raises one ValidationError with a sub-error group per branch, keyed by the branch class name. For the document that supplies no required group at all (the ninth parity case), the three groups read, in schema order:

CreateMediaBuyRequestExplicitPackagesWithFixedAllocation.packages
  Field required [type=missing, ...]
CreateMediaBuyRequestExplicitPackagesWithSellerOptimizedAllocation.packages
  Field required [type=missing, ...]      (and .total_budget, .budget_allocation)

Schema-derived text — the class names are the branch titles — and strictly more informative than the flat validator’s one sentence (“requires at least one of these field groups: …”), which named the groups but not what was wrong inside the nearest one. The two tests that match the old wording (tests/test_codegen_contract_compatibility.py:297 and :322, both match="at least one of these field groups") are asserting the message of a validator this design deletes; they are rewritten against the union error in the commit that deletes it (§7, commit 4), inside the 9.0 breaking window. A cross-branch mixture (e.g. packages + proposal_id) reports, per branch, the field that branch refuses — the absence hook names the offending key: proposal_id is not accepted by this request shape with the pointer, under the branch’s group.

5 · Consumer-facing cost, stated plainly

What breaks. adcp.types.CreateMediaBuyRequest (and 42 peers) stops being a class and becomes a TypeAlias union — the exact shape responses already have. Consequences, each loud, none silent:

  • CreateMediaBuyRequest(…) raises TypeError (a union is not callable). The migration table maps each flat name to its branch classes; the fix at a construction site is to name the branch being constructed — which is information the caller already had, since the flat constructor’s argument combination was the branch choice, implicitly and uncheckably.
  • CreateMediaBuyRequest.model_validate(raw) becomes TypeAdapter(CreateMediaBuyRequest).validate_python(raw). The SDK exports one cached adapter per union alias next to the alias (node-derived name: CreateMediaBuyRequestAdapter), so dict-shaped callers change one spelling. No factory function with 31 optional keywords is provided: that is the flat class again, reintroduced at runtime, and it makes nothing impossible.
  • isinstance(x, CreateMediaBuyRequest) keeps working (a union is a valid second argument), and issubclass-style registry checks need the member tuple.
  • Surface count: 43 flat names become 43 aliases + 124 branch classes (+ ~15 module-internal variant models with no public binding). The flat surface grows by the branch classes; every new name is schema-derived; the rename table for the response ordinals rides the same MIGRATION_v8_to_v9.md table, and aliases.py re-points as it did under PR #1374’s renumbering. 9.0.0 is in beta; this is the window.

What it does to our seller. Measured against prebid-salesagent at 4eedcb1de (pins adcp==6.6.0, so this arrives with the 9.x bump, not as a hotfix):

  • src/core/schemas/_base.py:2209 — class CreateMediaBuyRequest(BuyerRequest, LibraryCreateMediaBuyRequest) subclasses the flat class and narrows fields (packages → local PackageRequest, push_notification_config, brand). A union cannot be subclassed; the seller subclasses each branch class and declares a local union — the shape it already uses for responses (CreateMediaBuySuccess/CreateMediaBuyError extending the library branch classes, CreateMediaBuyResponse = CreateMediaBuySuccess | CreateMediaBuyError, same file). The narrowings land only on the branches that carry the field, which is itself a correction: today the proposal branch carries a dead packages narrowing.
  • src/core/tools/registry.py:129 — ToolSpec.dto: type[Req] and its issubclass(self.dto, BaseModel) check assume a class. The row type widens to accept a union alias; the registry builds one cached TypeAdapter per row at import; the AccountIdentity derivation (“the DTO requires account”) quantifies over the union’s members (all-of for required-ness, since every branch of these tools requires account at the root).
  • src/core/tools/_boundary.py:228 — TOOLS[tool_name].dto.model_validate(raw) becomes the row’s adapter: one line. serve()-style dispatch is otherwise untouched: the _impl annotation req: CreateMediaBuyRequest is still one name, and the body replaces optional-field sniffing (if req.proposal_id:…) with isinstance/match over branch classes — which mypy can check for exhaustiveness, a dispatch the flat class could not offer.
  • Inherited blast radius, measured previously and inherited unchanged: 31 SDK-side test failures, 28 of them fixtures encoding requests the bundled schema also refuses, concentrated in two shared factories (≈5 edits); and tests/test_decisioning_webhook_emit.py:497 carries a comment stating the incomplete validator’s contract as fact — those edits are corrections of fixtures that the defect itself taught, not accommodation of the new design.

8 · The strongest argument against this design

It multiplies classes without multiplying meaning, and it keeps the compiler anyway. 33 of the 124 branches belong to three schemas of the at-least-one-of idiom (control-media-buy-request 12, package-control 15, frequency-cap-constraints 6), where a branch is not an alternative a buyer chooses but a spec idiom for “supply at least one of these fields.” Those branches overlap: a document carrying paused and total_budget satisfies two of them, validation returns whichever matches first, and the instance’s class name then asserts an identity (“the paused update”) the document does not have. Fifteen near-identical public names replace one sentence of validator. And the runtime-check machinery does not disappear — 41 root conjuncts still need the compiler, the vocabulary module, and the closure rule — so the design pays the class multiplication and keeps a reduced constraint compiler.

The answer, in three parts. First, the identity noise is bounded and harmless by construction: in the at-least-one-of schemas every branch class carries the identical field set — only requiredness differs — so no data is lost whichever branch matches, left-to-right order makes the match deterministic, and nothing may dispatch on which at-least-one branch an instance is (there is nothing to dispatch on; the classes are evidence the group was satisfied, not routing). Second, the multiplication is not what the design is judged by — what it makes impossible is: all five measured defect classes stop having a spelling, where the flat shape plus any validator — including a complete one — leaves them spellable and merely refused, and the measured history of the flat shape is that its incomplete validator taught its wrong contract to the SDK’s own test suite (test_decisioning_webhook_emit.py:497) and to 28 fixtures. Third, the surviving compiler is not the old design surviving in disguise: its jurisdiction fell from every keyword of every root constraint (including all 247 branch-level occurrences) to 41 conjunct occurrences in 17 schemas, its output lands on classes whose shape already carries the branch content, and the closure rule it enforces is the same one either design needs for the next bundle’s unknown keyword. What would genuinely weigh against shipping is the same corner as before: a compiled predicate or a presence-ban whose semantics slip from JSON Schema’s on nulls or absent parents — and the suppliedness conventions, the per-primitive tests, and the parity corpus against the canonical validator remain the instruments that catch that first.
